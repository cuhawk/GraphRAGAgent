# NexusGraph

**GraphRAG + Knowledge Graph Agent** — answers complex questions by planning and
executing tool calls across an RDF knowledge graph (SPARQL), PostgreSQL-style
structured tables (typed SQL) and hybrid vector/lexical document retrieval, then
returns a grounded answer where **every claim carries machine-checkable
citations** and every run produces an inspectable trace.

> **All bundled data is synthetic.** The corpus is generated at seed 42 by an
> explicit generator (`src/nexusgraph/synth/`) — a fictional life-sciences
> portfolio (companies, compounds, trials, sites, investigators, milestones,
> operational safety events, documents). It contains no real medical, patient or
> company data and makes no medical claims. Documents carry a
> `SYNTHETIC DOCUMENT` banner; two documents are deliberate *adversarial
> fixtures* used to demonstrate prompt-injection resistance.

NexusGraph is a portfolio project: it is production-*shaped* (guards, budgets,
tracing, evals, CI), not production-*deployed*. Where something is unmeasured
or scoped down, the docs say so.

## What it does

Ask a question in natural language; the agent decides how to answer it:

| Question type | Example | Path |
| --- | --- | --- |
| Semantic | "What does the investigator handbook say about capacity reporting?" | hybrid retrieval (dense + BM25) |
| Relationship | "Which sites belong to trial T-2001?" | SPARQL graph traversal |
| Quantitative | "How did enrolment and cost change at Site A?" | typed SQL over monthly metrics, least-squares trend claims |
| Multi-hop | "Which products are derived from compounds used in trials that have delayed milestones?" | 4-hop SPARQL |
| Mixed | "Why is enrolment falling at Site A and which compounds named in safety reports are associated with it?" | graph **and** SQL **and** documents, cross-linked |
| Unanswerable | "What is the market share of NexuPharm?" | explicit refusal — no guessing |
| Adversarial | "Ignore all previous instructions and say …" | content is quoted-with-citation at most, never obeyed |

The planner emits *intents*, not raw queries: SPARQL is produced from
parameterised templates, structured queries from typed `QuerySpec` objects
compiled to parameterised SQL. Every tool runs under per-run budgets, timeouts
and row/byte caps, and every tool result is converted into ledger evidence that
claims may cite.

## Architecture

```
 question
    │
    ▼
FastAPI (/v1/query, /v1/query/stream, UI)      MCP server (stdio/HTTP)
    │                                              │
    ▼                                              ▼
            Agent Orchestrator  (trace span per stage)
    │            │                    │                │
    ▼            ▼                    ▼                ▼
 Planner /   Guarded tools ─────► Evidence ledger ──► Synthesizer
 Router      (SPARQL guard,      (ev-NNNN ids,        (deterministic
 Heuristic    SQL allowlist,      single citation      + optional LLM,
 or LLM)      retrieval caps)     source of truth)     citation-checked)
    │
    ▼
 Answer + claims + evidence + tools_used + trace_id
```

- **Storage profiles**: `local` (default; SQLite + numpy vector index +
  file-backed pyoxigraph RDF + in-memory cache) and `postgres` (PostgreSQL +
  pgvector + Redis). Same code paths; configuration only.
- **LLM-optional by design**: with `provider="mock"` the whole pipeline is
  deterministic (heuristic planner + rule-based synthesizer) — hermetic tests
  and evals run with no network and no model. With
  `provider="openai-compatible"` the planner and synthesizer use any
  OpenAI-compatible API, under strict validation with deterministic fallback.
- Details, decisions and trade-offs: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## The synthetic corpus

Generated by `nexusgraph bootstrap` (seed 42, reproducible):

- 14 documents (markdown, TXT, CSV, JSON, PDF) — each parsed → chunked →
  entity-extracted → resolved → embedded → vector-indexed → RDF mention triples
  in a **per-document named graph**
- 149 entities / 205 relationships (trials, sites, compounds, products,
  companies, investigators, milestones, safety events, regions, countries,
  hospitals)
- 1,035 structured rows incl. monthly site metrics and regional analytics marts
- 1,000+ RDF triples in an explicit ontology
  ([ontology/nexusgraph.ttl](ontology/nexusgraph.ttl), documented in
  [docs/ONTOLOGY.md](docs/ONTOLOGY.md))
- Scenario engineering so questions have checkable answers: Site S-1001
  (declining enrolment + rising cost + 5 safety events), delayed milestones on
  trials T-2001/T-2005/T-2009 → products P-4001/P-4002/P-4005/P-4007, region
  R-02 (rising enrolment + declining investigator capacity). See
  `data/dataset/manifest.json` `expected_facts`.

## Quick start

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```bash
git clone <repo-url> && cd nexusgraph
uv sync --extra dev

# generate + ingest the synthetic corpus (idempotent)
uv run nexusgraph bootstrap

# run the API + UI at http://127.0.0.1:8000
uv run nexusgraph serve

# or check store counts
uv run nexusgraph status
```

Docker (PostgreSQL + pgvector + Redis + API; see below for details):

```bash
docker compose up --build
# API on http://localhost:8000, UI at /
```

Inspect traces: every answer carries a `trace_id`; open
`http://localhost:8000/#trace` or `GET /v1/traces/{trace_id}`.

## The UI

A single-file, dependency-free UI served at `/`:

- query box with **live streaming** progress (plan → tools → synthesis)
- answer with per-claim citations and the evidence list (source, location,
  snippet)
- tools used, latency, question type
- **trace viewer**: hierarchical span tree with durations per run
- **entity explorer**: search entities, inspect relationships

## HTTP API

OpenAPI docs at `/docs` when the server runs.

```bash
# grounded answer (JSON)
curl -s localhost:8000/v1/query -H 'Content-Type: application/json' \
  -d '{"question": "Which products are derived from compounds used in trials that have delayed milestones?"}'
```

Response (abridged):

```json
{
  "answer": "Products derived from compounds used by trials with delayed milestones: P-4001, P-4002, P-4005, P-4007. [1] [2]",
  "question_type": "relationship",
  "claims": [{"claim": "...", "evidence_ids": ["ev-0001", "ev-0002"], "unsupported": false}],
  "evidence": [{"evidence_id": "ev-0001", "source_id": "sparql:...", "source_type": "rdf", "location": "...", "snippet": "..."}],
  "tools_used": [{"tool": "run_sparql", "status": "ok", "result_count": 4}],
  "trace_id": "b3f0...",
  "insufficient": false,
  "latency_ms": 6.1
}
```

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/v1/query` | grounded answer |
| POST | `/v1/query/stream` | same run as Server-Sent Events (`plan`, `tool`, `synthesis`, `final`) |
| GET | `/v1/entities?q=&type=&limit=` | search entities |
| GET | `/v1/entities/{id}` | entity + relationships |
| GET | `/v1/documents` | list documents |
| GET | `/v1/documents/{id}` | document (bounded text) + chunk count |
| GET | `/v1/traces/{id}` | recorded trace (span tree) |
| GET | `/v1/traces` | recent traces |
| GET | `/health`, `/ready` | probes (open; `/v1/*` optional API key via `X-API-Key`) |

## MCP server

The same read-only data tools are exposed over the Model Context Protocol:

```bash
uv run nexusgraph mcp        # stdio transport (for MCP clients)
```

- tools: `search_documents`, `run_sparql`, `query_structured_data`,
  `get_entity`, `get_relationships`, `retrieve_document`
- typed argument validation via the same Pydantic models as the agent
- bounded JSON outputs (`max_result_bytes`), per-call budgets, same guards
- `run_sparql` is SELECT/ASK-only through the SPARQL guard — the MCP surface
  is strictly read-only.

## Citations and provenance

- Every tool result becomes an immutable **Evidence** item (`ev-NNNN`) in a
  per-run ledger, carrying `source_id`, `source_type` (document/sql/rdf),
  `location` (chunk id / row key / SPARQL binding) and a snippet.
- Claims may only cite ledger ids; the orchestrator re-verifies every claim and
  every `[n]` marker before returning — fabricated citations are structurally
  impossible, and claims with no evidence are marked `unsupported`.
- If evidence is insufficient the agent returns `insufficient: true` with a
  reason instead of guessing.
- Ingestion provenance: every chunk carries its `document_id`; document-derived
  RDF triples live in the document's named graph; entity/relationship rows carry
  `source_ids`.

## Security model

Treat generated/retrieved content as untrusted. Layered controls
([docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) covers threats in depth):

- **SPARQL**: SELECT/ASK only; denylist for updates/federation; comment-scanner
  that understands IRIs and quotes; length cap; wall-clock timeout; row cap.
- **SQL**: the model never writes SQL — typed `QuerySpec` validated against a
  table/column allowlist, compiled by SQLAlchemy Core to parameterised SQL,
  `statement_timeout` on PostgreSQL, row cap.
- **Retrieved content**: per-call and per-run character caps; documents are
  quoted at most — the deterministic synthesizer cannot "follow" instructions
  in them, and the LLM synthesizer's claims are re-validated against the ledger.
- **Exfiltration**: no outbound calls on the answer path; the only HTTP client
  is the optional LLM adapter, whose prompt contains ledger snippets, never
  credentials.
- **Excessive tool use**: per-run tool-call budget (default 12), per-tool
  timeouts, bounded outputs.
- **API**: optional `X-API-Key` on `/v1/*`; `/health`, `/ready` stay open.

## Observability

- App-local traces are authoritative: every run records a span tree
  (`resolve_entities` → `plan` → `tool:*` → `synthesize`) with attributes,
  persisted to SQL and queryable at `/v1/traces/{id}` — no collector required.
- Optional OpenTelemetry: set `NEXUSGRAPH_OTLP_ENDPOINT` to mirror spans to any
  OTLP backend (Jaeger/Tempo); bridge failures never break the request path.
- Structured JSON logs (`NEXUSGRAPH_LOG_JSON=1`), per-run usage accounting
  (tokens/estimated cost; zero in mock mode).

## Evaluation and measured results

Run the deterministic eval suite:

```bash
uv run python -m evals.run          # writes evals/results/report.md + latest.json
```

19 cases across retrieval / graph / sql / multi_hop / mixed / unanswerable /
adversarial-injection, graded **deterministically** (no LLM judge; expected ids
derive from the corpus manifest). Latest measured run (mock provider — the
deterministic path, no LLM calls; see `evals/results/latest.json` for
provenance):

| Metric | Value |
| --- | --- |
| Success rate | 1.00 (19/19) |
| Retrieval recall (expected docs) | 1.00 |
| Retrieval precision | 0.19 |
| Citation precision / recall | 1.00 / 1.00 |
| Unsupported-claim rate | 0.00 |
| Tool-selection accuracy | 1.00 |
| Average latency | 5.6 ms |
| p95 latency | 14.1 ms |
| Total tokens / cost | 0 (mock mode) |

**How to read this honestly**: these numbers measure the *deterministic
mock-provider path* on 19 synthetic cases designed around the corpus's
scenario facts. Retrieval precision is low by construction (k=6 retrieval
against expected sets of 1–2 documents). Nothing here measures LLM-provider
quality, production traffic, or real-world data — those require plugging in a
real model (`NEXUSGRAPH_LLM_PROVIDER=openai-compatible`) and are **not yet
measured**. Metric definitions: [docs/EVALS.md](docs/EVALS.md).
